# Audit 2026-09: OSS wrappers and single points of failure

Read-only architecture audit, requested by the owner on 2026-09-21:

- **(A)** "Can we get by by making wrappers for any OSS tools or projects? If yes do it wherever possible
  across all modules."
- **(B)** "Single point of failure in the framework / product core functionality and its features'
  stability."

Verified against commit `da67e27` (main, 2026-09-21). Every claim below was checked by reading the code
named next to it; nothing was executed except `node` on a package-metadata script. Where a fact could not
be verified offline it says so. The rules applied come from `CLAUDE.md` ("Core philosophy", 2026-09-21):
wrap OSS by default for **new** work, hand-build only the differentiators (architecture rules/validator,
plan flows and impact, narrator and test generator, approval gate, workspace containment), swap existing
hand-rolled code **only where an audit shows a stability or maintenance win**, permissive licenses only,
one-way dependency direction (Cockpit -> core, never the reverse), no folder-structure changes.

### Policy for new work (what "wrap by default" means here)

1. Before writing a parser, a validator, a queue, a sanitizer or a protocol client, name the OSS package that
   does it and its license in the issue; hand-roll only if it is on the differentiator list or the package
   is heavier than the code it replaces (measure: transitive dependency count, not stars).
2. Core (`src/`) accepts zero-dependency or tiny (<= 4 transitive deps) MIT/BSD/ISC/Apache-2.0 packages; the
   Cockpit (`ui/`) may take larger ones. BlueOak/MPL need an owner decision (one such case exists today:
   `minimatch`).
3. Every wrapper is a block: JSON in, JSON out, `{ok:false,error}` never a throw, no `ui/` import from core.
4. Existing hand-rolled code is swapped only through an issue that names the stability or maintenance win
   and keeps the old tests green.

### Notes the tables could not carry

- **What is solid.** The approval gate's byte-for-byte binding, the workspace containment, the read-only
  review trees, the bot-worktree isolation and the process store's temp+rename all do what their headers
  claim, and the tests named in the tables cover the sharp edges (34 tests on the gate alone). The failure
  modes above are about *durability and operations*, not about the safety properties.
- **The hosted Cockpit is a single process on a single machine by design** (`run-hosted.sh` starts one
  client and one server, `Caddyfile.hosted` proxies both). That is acceptable for the MVP; the items above
  make a restart of that one process cheap (B1, B12) and a crash recoverable (B3, B4, B19).
- **The single most dangerous interaction found** is action #2: `heavy.sh` and a > 30-minute e2e run in
  another session. It explains why the preloaded project had to be renamed (`workspace.js` comment) and it
  will bite again on the next temp family that is not renamed.
