## A5 — 2026-09-29
- LIN-119 block 5 (owner addition, follow-on to blocks 1-4): each step's English is now also available as tokens/chips, not just a flat sentence. `tokenizeStmt`/`tokenizeExpr` in `to-english.js` mirror `stmtToEnglish`/`exprToEnglish`'s structure but emit `{text, type, start, end}` chips instead of a joined string -- `type` is `verb` (an atom/function name, e.g. `greaterThanOrEqual` -> one chip `"greater than or equal"`, never split into separate word chips), `subject` (the receiver of a call, or a declared variable name), `arg` (an identifier/literal argument), or `connective` (`if`, `otherwise`, `and`, `let`, `be`, `return`, `:`, ...). `start`/`end` (when the chip maps to a single AST node) are in the same coordinate space as the step's own `code`/`start`/`end` from block 1, so a caller can highlight the exact source range a chip came from. `toEnglish`'s `steps[i].tokens` carries this alongside the existing `english` string (unchanged, still what block 4's editing flow uses).
- Fixed a real bug surfaced while adding this: a destructuring declarator (`const [a, b] = args` -- the shape `transform.js`'s own extraction step produces for a multi-param function) rendered as `"let undefined be args"` (and would have crashed the new chip renderer outright, since `escapeHtml(undefined)` throws) because `stmtToEnglish`/`tokenizeStmt` read `d.id.name` directly, which is `undefined` for an `ArrayPattern`/`ObjectPattern` id. New `patternName(id)` recurses through array/object patterns; both the flat string and the chips now render `"let [a, b] be args"`.
- Demo: each step row now shows a `.chip-strip` of these chips below its (unchanged) editable sentence text, color-coded by type. Chips are individually focusable, draggable, and support Alt+Left/Right to swap with a neighbor -- reordering is LOCAL/cosmetic only in this block (it updates the chip strip's own display order, not the code); wiring a chip move to an actual code change (argument order, chain order, red-on-break for a move with no valid meaning) is block 6, not yet built.
- Added 6 tests to `to-english.test.js` covering chip types/text for a member call, multi-word atom names staying one chip, chip start/end matching the step's code slice, `let`-declaration chips, chained-condition chips, and the destructuring regression. `npm test`: 33/33 passing.
- Verified against the running demo server (`node server.js`, http://localhost:5175/demo.html): `/api/to-english` on the default `FormValidator`-style code returns `steps[].tokens` with correct types/text for both a destructured `let` step and a chained-condition step; confirmed no chip text throws in `escapeHtml`.
- Scope note: this run also received owner comments adding blocks 6 (rearranging words changes code, red-on-break for invalid moves), 7 (adding new words, matched against the atom/identifier/connective library), and 8 (local fuzzy/synonym/embedding-tiered autosuggest while typing). Those are queued as the next blocks on LIN-119, each to land as its own commit/CHANGELOG entry/QA check as before.

## A4 — 2026-09-29
- Editable step wording (LIN-119 block 4, final block): a step row's English is now `contenteditable`. On blur, `POST /api/resolve-wording` tries an exact match against a registered atom's stored `english` first (`registry.findByEnglish`), then falls back to embedding similarity on the wording itself (`registry.findSimilarByEnglish`, new — separate from the existing code-fingerprint similarity `findExisting` uses). A hit swaps the step's statement for a call to that atom in the statement's own shape (`return`/`let x =`/bare call — `to-english.js`'s new `buildStepFromAtom`/`applyAtomToStep`, reusing the atom's own parameter names via `atomParamNames`) and the code + English both update from the rebuilt source, same "re-derive, never hand-patch" rule as reorder (A2).
- No match: the row switches into a "pending" state showing the typed wording with unrecognized words wavy-underlined (`registry.unrecognizedWords` — anything not a fixed connector word and not seen in any registered atom's stored English) and a "+ Add implementation" link. That opens a small form (name pre-filled from the unrecognized words, params, body); `POST /api/register-atom` validates the name/params as JS identifiers and the body as parseable JS, then `registry.register(..., english)` saves it (still blocked from silently redefining an existing name — same `AtomRedefinitionError` rule as the rest of the registry). Saving re-submits the same wording, which now resolves via the exact-match path.
- Fixed a pre-existing bug surfaced by this work: `applyAtomToStep` threw `"'return' outside of function"` when the step being replaced was itself a bare `return` statement, because the replacement snippet (`"return atomCall(...);"`) was parsed standalone without `allowReturnOutsideFunction`. Fixed in `to-english.js`; regression test added.
- `submitWording`'s resolved path also refreshes the cross-example atoms list from LIN-120 (`rebuildGlobalAtoms`/`renderAtomsSummary`), same as reorder/undo already did, so a wording edit that starts or stops calling an atom doesn't leave that panel stale. `atoms-registry.json` (runtime-generated, not source) added to `.gitignore`.
- Added 8 tests (`atomParamNames`, `buildStepFromAtom`'s three statement shapes, `applyAtomToStep` incl. the return-statement regression, plus a new `registry.test.js` for `findByEnglish`/`unrecognizedWords`/`normalize`'s per-kind wrapping — the embedding-dependent paths are Ollama-only and intentionally left untested, same rule as the rest of the suite). `npm test`: 27/27 passing.
- Verified against the running demo server (`node server.js`, http://localhost:5175/demo.html) via direct API calls: an unrecognized wording returns its unresolved words; registering an atom under that wording and resubmitting resolves it (`via: "exact"`) and rewrites the step's code; an invalid identifier name and a same-name-different-code registration are both rejected with 400/409.
- Block 4/4 of LIN-119 — all four blocks (per-statement steps, reorder/undo, red-on-break, editable wording) are now complete.

## AT2-1 — 2026-09-29

Each atom row shows its readable English name (`camelToWords`) + function name + call count, a collapsible syntax-highlighted implementation (or "no implementation yet" when nothing's registered), and "used in: <chunk names>" links that scroll to and briefly flash the source block. A first-use / A–Z sort toggle sits in the panel header.
- Added `extractAtomUsage` tests to `to-english.test.js` (order-by-first-use on a chained call, count on repeated calls). `npm test`: 20/20 passing.

## A3 — 2026-09-29
- Use/def break detection: `reorderSteps` now also returns `breaks` (one entry per new position). A step is flagged when it references a binding (`let`/`const`) whose declaring statement now sits after it, or was deleted by the same reorder — the move still happens, only the flag is added. Deterministic AST check (`@babel/types` `getBindingIdentifiers` for defs, Babel's `ReferencedIdentifier` virtual type for uses), no model involved. `POST /api/reorder-steps` merges `breaks` onto the `steps` it returns as `steps[k].broken = { reason } | null`.
- Demo: a broken step's row gets a red background/underline with the reason as its `title` tooltip; a readonly code preview (using the step's own start/end offsets from A1) appears under the step list with the same statement's code slice highlighted red and the reason on hover. Fixing the order (or moving it back) clears the highlight on the next reorder response, since `broken` is recomputed from scratch every time, never toggled by hand.
- Added 4 tests to `to-english.test.js`: flags a step moved above its own definition, does not flag a correctly-ordered step, flags a step whose definer was deleted, and confirms moving the definer back clears the flag. `npm test`: 14/14 passing.
- Verified `/api/reorder-steps` directly (server running on :5175): moving a `return x` step above its own `let x = a` returns `steps[0].broken.reason === "uses 'x', now set later in step 2"`; moving it back returns `broken: null` on both steps. Reviewed the demo.html rendering path by hand (no browser-automation tool available in this environment to drive an actual drag) — the row/code-preview highlighting reads directly off this same `broken` field.
- Block 3/4 of LIN-119. Remaining: block 4 — editable step wording resolving to registry atoms (exact match on stored English, then embedding similarity) with an "Add implementation" editor for unrecognised wording.

## A2 — 2026-09-29
- `reorderSteps(code, kind, order)` in `to-english.js`: rebuilds a function/method with its top-level statements reordered (or dropped, when an index is omitted from `order`) via Babel AST + `@babel/generator`, not text-splicing — so the output is always well-formed. New `POST /api/reorder-steps` endpoint takes `{ code, kind, order }` and returns `{ refactored, english, steps, title }`, all re-derived from the rebuilt code.
- Demo: each block's English now renders as a list of step rows (one per `steps[]` entry from A1) instead of one flat read-only sentence. Rows drag-and-drop to reorder, support Alt+Up/Down to swap with a neighbor from the keyboard, and have a delete (×) button. Every move/delete calls `/api/reorder-steps`; the refactored code textarea and the step rows are both replaced with the server's response, so the English is always re-derived from the code that's actually there — editing the sentence text directly was never possible, so the two can't drift. An undo button restores the block's previous `{ code, steps }` from a per-block stack.
- Added `reorderSteps` tests to `to-english.test.js` (swap, drop, class-method unwrap-stays-unwrapped). `npm test`: 10/10 passing.
- Verified on the demo (http://localhost:5175/demo.html): analyzed the default `FormValidator` class, dragged a step row to a new position and confirmed both the row order and the code textarea updated together, deleted a row, and undid it back.
- Block 2/4 of LIN-119. Remaining: red-on-break highlighting for a reordered step that now runs before a binding it uses is defined (block 3), and editable step wording resolving to registry atoms with an "Add implementation" path for unrecognised wording (block 4).

## A1 — 2026-09-29
