## B2 — 2026-09-29

Found via a real crash while writing this block's own tests (a 2-param function's plugged form has one more statement than its source), fixed before commit.

## A6 — 2026-09-29
- LIN-119 block 6: reordering a step's word chips (block 5) can now change the code, deterministically, for exactly one case -- two `arg` chips swapping position within the same call's argument list. `reorderChip(code, kind, stepIndex, order)` in `to-english.js` re-tokenizes the step, finds the two chip positions the requested `order` actually displaces (not necessarily adjacent -- a connective usually sits between two argument chips), and applies the swap directly to the matching `CallExpression.arguments` nodes, then regenerates via Babel. Anything else -- a connective or verb chip involved, the two chips arguments of different calls, more than two positions displaced at once -- returns the code UNCHANGED plus a `broken` reason string; there is no deterministic code meaning for those moves, so none is invented. `POST /api/reorder-chip` (`server.js`) wraps this and folds the reason onto that step's existing `broken` field (same shape reorder-steps already returns from block 3), re-deriving `english`/`steps`/`atomUsage` from whatever code resulted either way.
- A bug in my own first pass at the "is this a single swap" check shipped and was caught by its own test before commit: it rejected any order with a connective correctly untouched between two swapped chips (the common case, since args are almost always chip-separated by "and"), because the loop bailed out on seeing a SECOND displaced position instead of confirming it was the FIRST one's partner. Fixed to collect all displaced positions and check there are exactly two, each other's target.
- Demo: chip moves (drag or Alt+Left/Right) now always move visually first, then `POST /api/reorder-chip` decides the rest -- a resolved swap updates the code/English/atoms-summary from the server's rebuilt source (undo-able, like every other mutation here); an unresolved one sets that step's `broken` reason and the row turns red (title tooltip), without reverting the chip's new on-screen position, matching the "the move still happens" rule from block 3. Each chip now carries a stable `origIdx` (its position as of the last server response) so a chain of local-only broken moves can never desync from what the server thinks the step's original chip order was -- `tagOrigIdx()` is called everywhere a fresh `steps` array comes back from the server (initial analyze, live-edit, reorder-steps, resolve-wording, reorder-chip).
- Added 4 `reorderChip` tests (valid arg-arg swap regenerates code; rejects arg+connective; rejects args from two different calls; rejects a 3+-position displacement). `npm test`: 42/42 passing (`unplug.test.js`, LIN-122 block 2 in progress on a concurrent session, is unaffected by and unrelated to this work).
- Verified against the running demo server (`node server.js`, http://localhost:5175/demo.html) via direct `/api/reorder-chip` calls: swapping two arguments of the same call regenerates `combine(a, b, c)` -> `combine(b, a, c)` with matching English; swapping an argument with an adjacent connective chip returns the code unchanged with a `broken` reason on that step.
- Deferred, noted as a known gap: chain-link reordering (`ifIt(x).equals(y).and(...)` -> reordering the `.equals()`/`.and()` links themselves) is NOT handled by this block -- a verb chip move always returns `broken` for now. Doing that safely needs each chain link modeled as one composite chip (verb + its own args moving together) rather than today's separate verb/arg chips, which is a real change to the chip model itself; left for a follow-up rather than bolted on here.
