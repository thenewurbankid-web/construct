This is a rule for this project, in addition to the global working agreement and the repo-wide ground rules in `../CLAUDE.md` (one dated daily branch per project as the sole release path, all work in worktrees, no progress monitoring for OG/Shashank — see that file for the full statement, set 2026-09-27/28).

## The main session is a brainstorming partner; agents build and one agent reviews

- The user and the main session **brainstorm**: they discuss what to build, weigh options, and settle scope. The main session **answers questions** and **hands work off to subagents**. It does not write or edit code, docs, examples or config itself.
- **Research is handed off too.** Anything beyond a quick lookup (web research, comparing products or papers, surveying the codebase, "what's the best approach") goes to a research agent (Explore for read-only work), with a cited, concise report. The main session does not research inline and does not present its own recollection as research.
- **Answers to the user are fast and short.** Answer in a few lines, lead with the answer, put detail behind an offer ("want the full comparison?"). Long write-ups come from agents, not from the main session. Set by the user on 2026-09-27.
- **Sessions, tokens and models (user, 2026-09-27):** do not raise session length, compaction or token usage in this project (the user has another account with tokens; this overrides the global long-session guard for this project). Never launch an agent with the `fable` model; leave the model unset so it inherits, or pick another model explicitly if there is a reason.

Every builder brief must include this. The Construct source is on `origin/main` of the parent repo (a read-only worktree exists at `/Users/shashank/Repositories/construct-worktrees/cockpit-main`). - Only launch an agent the user asked for. If the user stopped an agent, do not relaunch it unless they ask again.
- When an agent finishes, relay what it reported. Do not redo its work and do not review it yourself.
- Exceptions: recording an instruction the user just gave (this file, the memory notes), and any task where the user says "do it yourself".

## Default workflow: iterative co-work in a dedicated worktree (user, 2026-09-27)

This is the default mode now, for UI work and anything else the user wants to iterate on closely, and it supersedes the batching-only reviewer rule below for this mode. The user and the main session brainstorm and decide; the main session and the user never write code. Per thread of work (e.g. "Studio UI polish"):
- One dedicated worktree for the whole thread, created once and reused across increments (not a fresh worktree per increment).
- The user gives one small increment of direction at a time. The main session turns it into a self-contained builder prompt, launches one builder, then the reviewer checks that increment specifically before the next one starts — review is per-increment here, not batched across several builders as the section below still describes for independent parallel tracks.
- The main session relays the builder's and reviewer's reports, and the two of them decide the next increment together.
- Other Trace work keeps moving independently in its own worktrees at the same time, unaffected by this thread's pace.
- This is Trace-side work; unless the user says otherwise, a thread here does not touch Construct/Cockpit.

## Review is done by one reviewer agent, not by the main session

- Set by the user on 2026-09-26. **One** reviewer agent (a general-purpose agent, read-only in practice) reviews the work of **all** the builder subagents on the user's behalf. The main session does not review either.
- Launch it once, after the builder agents it covers have reported, with the worktree paths, branches and each builder's original task. Do not launch a reviewer per builder. (Exception: the iterative co-work mode above reviews each increment individually, by design.)
- The reviewer's brief (use it every time): check each builder's result against its original task and the project rules (deterministic core, no guessing, existing examples' output unchanged); run `npm test` and compare with the baseline given in the task; open the changed files and read the diff; run the feature in a real browser or CLI where the task says to; look for merge conflicts between the branches and with the main copy; confirm claims in the builder's report rather than trusting them. It must not edit files (findings only) and must report per branch: verdict (ship / fix first / reject), what it verified and how, what it could not verify, and a ranked list of problems with file and line.
- The main session relays the reviewer's report unchanged, and says which claims the reviewer could not verify. If the reviewer finds problems, the fix goes to a builder agent, then back to the reviewer.

## Setup (how the rules above are wired)

- **Agents** live in `.claude/agents/`: `builder` (writes files; one per piece of work; prompt states scope, rules, `npm test`, no commits, report under 300 words) and `reviewer` (read-only: Read, Grep, Glob, Bash; the one reviewer above; brief is in its file). Use these two rather than general-purpose. New agent files need a Claude Code restart the first time.
- **Hook**: `.claude/settings.json` runs `.claude/hooks/orchestration.mjs` before Edit, Write, NotebookEdit and Bash. It denies the main session's file writes inside `line-matcher/` (a subagent is recognised by `agent_id` / `agent_type` in the hook input). Always allowed: subagents, `CLAUDE.md`, `.claude/**`, the memory directory, and any path outside `line-matcher/`. It fails open on anything unexpected. The Bash guard is best-effort: it catches obvious writes (`sed -i`, `>`, `tee`, `cp`/`mv`/`rm`, `git commit`/`checkout`/`reset`, `npm run generate`/`install`), not scripts or interpreters that write files. Tests: `node --test .claude/hooks/orchestration.test.mjs`.
- **"Do it yourself"**: switch the hook off with `touch .claude/orchestration-off` (or start Claude Code with `LM_ORCH_OFF=1`); switch it back on with `rm .claude/orchestration-off`. Writing that file is allowed for the main session. Turn it back on when the task is done.
- **Worktree recipe** (when the user asks for a separate worktree): `git worktree add -b <branch> /Users/shashank/Repositories/construct-worktrees/<name> HEAD`, then rsync `line-matcher/` into `<worktree>/line-matcher/`, excluding `subframe-app/node_modules`, `tools/jev/.venv`, `tools/jev/open-jev` and `demo-app/node_modules`. Point the builder at that directory.
