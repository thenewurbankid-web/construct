# T23 — the structural-coincidence gate

Behind the `--structural` CLI/pipeline flag (off by default). Referenced from code comments in
`src/structural.mjs` and `src/structural-gate.mjs`; this file is what those comments point to.

## What it catches

The matcher accepts a part when exactly one transform reproduces the design's text. Some of those
explanations are only right because of how the *mock* data happens to be built, not because they are
what the design means. `src/structural.mjs` runs four pure detectors over such a single-candidate
accept:

| pattern | fires when |
|---|---|
| `count-equals-row-count` | the match is `count()` of the list, and the design's number equals the mock list's row count |
| `sequence-equals-id-or-index` | the design shows a running number (1, 2, 3, ...) and the matched field is an id, or itself runs one-by-one down the list |
| `extremum-is-overall-extreme` | the match is `max`/`min` of a field over the whole mock list |
| `small-number-from-envelope` | the design shows a bare small whole number (≤3 digits) that happens to equal one scalar of the response envelope |

If a detector fires, `src/evidence.mjs` compares the design's own label words for that part against
the field's name/contract docs (`src/labels.mjs`, `fieldDocsOf()` in `src/openapi.mjs`):

- **supports** — the design's wording agrees with the field name. The accept stands; the rule and the
  evidence are recorded on the part (`part.structural`), nothing is asked.
- **contradicts** or **neutral** — the design's wording does not vouch for it. The accept is *not*
  made silently; the part becomes a question instead.

Parts no detector fires on are untouched — a page with no flags generates exactly what it always did.

## The confirm-or-pick question

When a flag is not supported by the design's own words, the part renders as the `confirm-or-pick`
form (`src/questions/forms.mjs`), chosen by `partFormId()` when `flagged` is true — it wins over the
plain `--ask-all` "keep or change" question because it carries the coincidence reason.

Shape:

> `<part>` matched `<the one candidate explanation>`, but that could be a coincidence: `<risk text —
> the detector's reason plus what the design's words do/don't support>`. The design shows `<the
> design's example text>`. Confirm it, pick another explanation, or leave it as a gap?

Options, in order:

1. **Confirm** the flagged candidate (accept it after all).
2. **Pick instead** — one option per other explanation that also reproduces the text, cheapest first
   (`rank()` in `src/structural-gate.mjs`; the matcher's normally-discarded alternatives).
3. **Leave it as a gap** — a TODO to answer later.

In auto mode (no interactive answer), the part stays open with the reason recorded in the hint
(`NEXT_STEP` in `src/structural.mjs` gives the plain-words next step per pattern).

## Where it renders today

The question is built by the existing generic wizard question list (`src/ask.mjs`, backed by
`src/questions/forms.mjs`) and travels to the browser as a normal `"question"` event (`src/pipeline.mjs`),
now carrying `form: "confirm-or-pick"` alongside it. The demo shell (`src/ui/demo.mjs`'s `askCard()`) renders
it with a dedicated layout instead of the generic flat button list: Confirm as a primary action, the "Pick
instead" alternatives as a labeled secondary group, and "Leave it as a gap" as a de-emphasized ghost action,
under a short "Coincidence flagged" badge (`src/ui/confirm-or-pick.mjs`). The interactive terminal wizard
(`src/ask.mjs`'s own prompt loop) and `src/ui/endpoint-select.mjs` (an unrelated, API-endpoint-picker wizard)
still show it as plain numbered options.
